# PRODUCT_METRICS 产物与发布契约

第一次写入门户前读取，并同时遵守 `$document-publisher` 的当前正文契约、能力注册表、发布和预览流程。这里仅定义产品指标文档的业务内容与增量范围，不复制发布器的通用实现规则。

## 稳定属性

```text
source: docs/gainfactor/{product-slug}/product-metrics.mdx
presentation: docs/gainfactor/{product-slug}/product-metrics.portal.json
artifact: product-metrics
type: Product-Metrics
layout: report
```

三次阶段交付复用同一文件和 artifact 身份，不创建三份文档，不覆盖门户内其他内容。必须写入上游 `PRODUCT_DEFINITION` 所在工作区；group、collection、route 和默认门户由 `$document-publisher` 统一计算。产品指标作为该产品下面的“产品指标分析”子文档，不得回落到“其他文档”或按文档类型分组。

预期左侧导航：

```text
产品名
├── 产品定义
└── 产品指标分析
```

## 最终正文

```markdown
## 指标体系结论
## 产品价值与测量目标
## 核心指标体系
### 主要指标
### 指标驱动树
### 过程指标
```

未开始阶段不写空标题、空表格或占位内容。

主章节不使用 `0.`、`1.` 等数字前缀。增量阶段尚未生成后续章节时，数字编号会形成跳号并干扰目录理解；稳定章节名称本身承担导航语义。

### 内容边界

1. **摘要**：任务、主要指标、首要杠杆、首要底线、两个状态和最重要缺口；
2. **产品价值与测量目标**：上游链接、一句话价值、精简价值链和本次任务，不重复完整产品定义；
3. **核心指标体系**：最终主要指标、驱动树、最终过程指标和精简虚荣指标提醒；
4. **底线与错误激励**：最不能发生的事、最终底线和精简伪底线提醒；
5. **如何计算和使用这些指标**：只保留业务问题、通俗定义、通俗公式、示例、当前状态和行动；
6. **数据实施附录**：集中提供最终指标的技术公式、实体、事件、字段、ID、去重、归因、异常、回填、来源和责任人；
7. **执行状态与缺口**：只写影响使用的数据、基线、阈值、权限、责任或证据问题及下一步动作。

完整相似产品研究、淘汰候选、逐项通过的门禁、搜索过程、中间材料和用户确认对话不进入门户。研究只保留实际改变最终判断的一小段依据与来源。复杂研究确需复核时才保存到不进入门户的 `docs/gainfactor/{product-slug}/.work/product-metrics.research.json`；普通任务不创建 sidecar。

## 表格字段

- 核心指标：指标、它回答什么问题、与主要指标关系、当前能否可靠使用、对应行动；
- 虚荣指标：指标、为什么容易误导、正确诊断用途、替代价值信号；
- 底线指标：指标、最不能发生的事、红线阈值、阈值依据、击穿后果、响应动作；
- 伪底线：指标、为什么不是真底线、实际类型、替代信号；
- 指标总览：指标、它回答什么问题、通俗公式、当前能否可靠使用；
- 执行缺口：指标 ID、缺口、影响、补充动作、责任人、目标时间。

主表不放 `COUNT(DISTINCT ...)`、字段名、事件名、数据源和责任人等实施信息，避免形成无法阅读的宽表。每个最终指标在主表之后按业务名称展开业务说明；全部技术细节统一放到“数据实施附录”，不在业务说明中重复。公式与数据定义不跨章节重复。

### 表格布局门禁

- 门户正文表格默认不超过 5 列；超过 5 列时必须拆表或改成纵向详情。
- 不把公式、数据定义、来源和责任人同时放进一张横向表格。
- 单元格预计超过两行时，优先移到指标详情小节；表格只负责扫描和比较。
- 不允许表头或正文出现中文逐字竖排、内容被挤压到单字宽度或依赖横向滚动才能理解。
- 核心指标总览推荐 4 列：`指标 / 它回答什么问题 / 通俗公式 / 当前状态`。
- 过程指标推荐 4 列：`指标 / 推动什么 / 如何计算 / 变化后怎么做`。
- 底线指标推荐 5 列以内；阈值依据和响应细节过长时移到对应指标详情。
- 数据实现采用纵向字段、定义列表或短表，不建立包含 ID、类型、公式、数据摘要、两个测量状态、窗口、来源和责任人的十列宽表。

## 标题规则

标题必须先让读者知道“这是什么指标、帮助判断什么”，不能使用 `指标 ID + 完整测量契约` 作为可见标题。

使用：

```text
### 候选明确采纳率：用户是否愿意采用推荐结果

指标编号：PM-P-002
指标类型：核心过程指标
```

避免：

```text
### PM-P-002 完整测量契约
```

推荐的固定标题语言：

| 技术式标题 | 面向读者的标题 |
|---|---|
| 指标字典 | 如何计算和使用这些指标 |
| 数据定义 | 计算这个指标需要哪些数据 |
| 可统计性与可衡量性 | 当前能否可靠使用这个指标 |
| 判断与行动 | 指标变化后应该怎么判断和行动 |

指标 ID 是辅助定位信息，不承担标题语义。标题中不得只出现编号、“完整测量契约”“口径详情”等内部术语。

页面一级标题和左侧子文档标题统一为“产品指标分析”，不使用“产品指标：产品名”；产品名称由父级导航分组与 `Product` 元信息表达。

## 单个指标的正文结构

```markdown
### 指标名称：它帮助回答的业务问题

指标编号与类型

一句话说明普通人如何理解。

**通俗公式**：成功对象数 ÷ 全部机会对象数 × 100%

> 示例（非真实数据）：……

**当前状态**：……

**指标变化后怎么做**：……
```

业务正文中的单个指标控制在一个屏幕内，不连续堆叠 7–10 个项目符号。“如何计算”先展示通俗业务公式，并在必要时提供一个标记为非真实数据的简单示例。技术公式、字段、事件、ID、去重、归因和回填规则只能进入“数据实施附录”。

推荐用 `Panel` 或短小节呈现一个指标：标题使用业务名称，`eyebrow` 放指标 ID，`description` 解释业务问题，短字段只放类型和当前状态，正文承载通俗公式、示例与行动。不要把完整测量契约塞入 `fields`，也不要为每个字段创建一条项目符号。

## 数据实施附录结构

附录明确写明“供数据、工程和分析人员实现口径使用，普通读者可跳过”。每个指标使用业务名称作为标题，ID 放在标题后的辅助位置：

```markdown
### 有效需求承接率的数据实现

指标编号：PM-P-001

#### 技术公式
#### 数据对象与事件
#### 去重、归因与异常
#### 窗口、刷新与责任
```

相关字段使用短表或分组定义，不使用一条包含全部内容的超长公式，也不把多个指标的实现连续写成无分组的项目符号墙。附录中的技术公式必须允许换行；公式较长时使用 fenced code block，不使用超长行内代码。

## 表达设计

根据阅读任务选择 `$document-publisher` 已注册的组件，不固定堆叠组件：

- 摘要适合紧凑信息网格；
- 复杂价值链和驱动树适合 Mermaid，简单关系使用文字；
- 最终主要指标适合突出展示；
- 过程、底线和指标总览使用精简表格，技术细节进入单指标的数据实现小节；
- 不可接受失败和高影响缺口适合警示 Callout；
- 图标只用于帮助识别主要、过程、底线和数据定义，不代替可见文字。

表格负责精确，图形负责关系，正文负责解释，三者不机械重复。Manifest 只能重组正文已有事实，不引入新的指标、状态或结论。

### 可读性门禁

发布前从普通产品读者视角检查：

- 首屏后 3 分钟内能否理解北极星、三个主要杠杆和首要风险；
- 是否出现连续两屏以上的项目符号契约；
- 是否先看到技术字段，再看到指标含义；
- 是否存在超过视口宽度的行内公式；
- 是否能跳过数据实施附录而完整理解指标体系；
- 相邻指标是否有清楚的视觉分组，而不是仅靠编号区分。

任一项失败都要重写结构，不能以“内容完整”为由通过。

### 可见状态文案

稳定元信息继续使用英文枚举，但面向读者的摘要、卡片、Callout 和表格必须显示中文：

| 稳定值 | 可见文案 |
|---|---|
| `proposed` | 待确认 |
| `confirmed` | 已确认 |
| `unverified` | 待验证 |
| `partially-ready` | 部分就绪 |
| `ready` | 已就绪 |

不要在首屏和正文摘要直接展示 `Definition Status`、`Measurement Readiness`、`process-metrics-confirmed` 等内部枚举；改写为“定义状态”“测量准备度”“当前阶段”等读者语言。

## 三次增量写入

| 阶段 | 写入内容 | Stage |
|---|---|---|
| 主要指标确认 | 摘要、价值与目标、最终主要指标、主要指标业务说明与实施附录 | `primary-metric-confirmed` |
| 过程指标确认 | 更新摘要，加入驱动树、过程、虚荣指标，并更新业务说明与实施附录 | `process-metrics-confirmed` |
| 底线指标确认 | 加入底线、伪底线，补全业务说明、实施附录和执行缺口 | `complete` 或 `complete-with-gaps` |

每次用户确认后自动调用 `$document-publisher`：

1. 直接创建或更新最终 MDX 与可选 Portal Presentation，不先生成普通 Markdown 再转换；
2. 从实际路由读回标题、阶段、主要指标、两个状态和当前阶段内容；
3. 执行发布器 preview 动作，已有服务时复用，未启动时按发布器流程启动；
4. 检查正文、图表、组件、图标和当前路由可访问；
5. 返回预览地址与文档路由。

写入或预览失败时保留已成功内容，报告具体阻塞，不声称发布成功。用户明确要求只在对话中输出、不要写入或不要启动服务时，按其要求缩减交付。

## 最终准出

- 上游用户、问题、价值机制和有效结果可追溯；
- 指标任务明确，长期体系只有一个北极星；
- 主要指标不是从现有数据倒推；
- 最终指标公式、数据定义、可统计性和可衡量性完整；
- 驱动关系、行动和错误激励可解释；
- 底线对应真实失败，阈值与响应状态诚实；
- AI 产品的价值模式、失败和成本信号一致；
- Definition Status 与 Measurement Readiness 没有混写；
- 同一 slug 的正文、阶段和 Presentation 一致；
- 产品指标位于上游产品同名一级导航下，子文档标题为“产品指标分析”；
- 所有表格通过列数、换行、溢出和移动端门禁，没有逐字竖排；
- 普通业务正文不存在连续契约项目符号墙，技术细节集中在可跳过的数据实施附录；
- 实际路由读回与预览通过。
