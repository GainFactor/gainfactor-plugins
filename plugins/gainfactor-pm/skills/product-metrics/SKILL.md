# Product Metrics

> **语言规则**：默认跟随用户输入语言；用户显式指定时以用户指定为准。稳定 artifact type 使用 `PRODUCT_METRICS`。详见 `../../references/language-policy.md`。

从产品已经承诺的用户价值出发，定义能够支持真实决策的主要指标、过程指标和底线指标。每个核心指标都必须说明它代表什么价值、支持什么决策、如何计算，以及变化后团队采取什么行动。

## 输入与边界

优先读取已有 `PRODUCT_DEFINITION`，复用其中已确认的用户、问题、价值机制、角色、核心场景、可观察结果、生命周期、商业模式和失败边界，不重复询问。

- 没有产品定义，或核心用户、问题、价值机制存在高影响冲突时，说明阻塞并建议先运行 `$define-product`。
- 上游为 `analysis-target` 时，默认只分析公开可观察的候选指标；若要为该产品制定内部指标，先确认用户拥有该产品或已获授权。
- 本 Skill 不改写 `PRODUCT_DEFINITION`。指标文档作为独立下游 artifact，与上游门户路由建立关系。
- 本 Skill 不实现埋点、数据管道、看板、实验平台或绩效制度，也不诊断已有指标为什么变化。

## 总体流程

```text
读取 PRODUCT_DEFINITION
→ 建立产品价值链并通过门禁
→ 与用户确认指标任务
→ 生成主要指标候选并通过门禁
→ 用户确认，第一次写入门户
→ 拆解公式、驱动树和过程指标并通过门禁
→ 用户确认，第二次更新门户
→ 定义底线指标和行动契约并通过门禁
→ 用户确认，第三次更新门户并完成
```

每个阶段只询问当前阶段会改变结论的问题。用户确认的是指标业务定义，不是是否生成或发布；阶段确认后自动更新同一个文档。

## 阶段一：建立产品价值链

从上游提取并连接：

```text
核心用户 → 触发场景 → 核心行为 → 有效结果 → 持续价值 → 商业或组织战略结果
```

多边产品分别建立关键角色价值链，再寻找共同价值交集；内部效率产品以任务改善、采用、时间／质量／成本变化和组织目标收束，不强行连接营收。

用 Mermaid 展示关系，并在图前说明阅读目的、图后概括价值真正发生的位置。只有核心对象、有效结果、因果关系、多边价值和上游一致性通过门禁，才进入下一阶段。

## 阶段二：确认指标任务

向用户展示价值链后，只确认本次需要支持的任务：

- **长期产品指标体系**：定义一个唯一北极星指标；
- **上线或采用判断**：定义一个主要成功指标及采用和上线底线；
- **专项优化**：定义一个专项结果指标、关键驱动和反向指标；
- **实验评估**：定义一个主要实验指标、必要诊断指标和实验底线。

统一称为“主要指标”。只有长期产品指标体系的主要指标称为“北极星指标”；其他任务不得为了形式强行命名为北极星。

同步确认指标需要支持的决策、决策角色和评审周期。上游没有且会影响选择时，再确认产品阶段、战略目标、已有候选、历史基线和关键数据限制；每轮最多 2 个相关问题。

## 阶段三：定义主要指标

按以下路径生成候选：

1. 明确产品解决的最核心问题和有效结果；
2. 梳理多边角色的价值交集，或单边产品不同核心群体的共同价值；
3. 研究 3–5 个真正具有参考价值的相似产品，比较价值机制、用户网络、商业模式、使用频率和公开经营指标；
4. 将官方公开指标、公开经营指标和分析推断严格分开，不把未公开指标写成事实；
5. 生成 2–3 个候选，比较价值代表性、战略关系、决策相关性、反馈速度、可影响性、可测量性和抗博弈性；
6. 推荐一个候选进入主要指标门禁。

长期产品指标体系还要检查该指标是否代表关键角色共同成功，并与长期商业结果或组织目标正相关。内部效率产品检查组织价值，不检查营收。

按参考文件逐项执行门禁，使用 `✅`、`⚠️`、`❌` 展示结果。关键门禁不通过时返回候选池，最多再比较 2 个替代候选；仍无法通过则标为 `待定义`，不伪造最终答案。

使用候选比较表、门禁表和必要的 Callout 向用户展示可审计的决策依据，不输出隐藏的内部推理过程。用户确认后，创建或更新同一 `PRODUCT_METRICS` 文档，写入价值链、指标任务、相似产品、候选比较、最终主要指标和门禁结果。

## 阶段四：公式、驱动树与过程指标

将已确认的主要指标定义为可复算公式，至少明确分子、分母或计数对象、纳入与排除条件、去重方式、统计窗口、刷新频率、数据来源和责任人。

根据产品类型、用户网络、价值机制和主要指标公式建立驱动树。选择 3 个真正能够推动主要指标、适合当前决策周期且团队可影响的核心过程指标；每个指标说明稳定 ID、业务定义和公式、因果假设、统计窗口、数据来源、期望方向、对应行动，以及刷高或误读风险。

再列出 2 个当前产品最容易误用的虚荣指标，说明它们何时只能作为诊断信号，以及应替换为哪个价值指标。3 个过程指标是完整体系的默认；局部任务只保留会改变决策的必要指标，不为凑数增加。

过程指标通过驱动关系、可影响性、反馈速度、可计算性、非重复性、错误激励和行动性门禁后，用 Mermaid 驱动树和精确表格向用户展示。用户确认后更新同一门户文档，增加公式、驱动树、过程指标、门禁和虚荣指标。

## 阶段五：底线指标与行动契约

先回答：“即使主要指标增长很好，发生什么事情时我们仍会认为产品失败？”从产品责任边界、用户信任、角色失衡、质量、成本、履约、合规和 AI 失败方式中寻找不可接受失败。

输出 3 个真正制衡主要指标的底线指标，每个说明稳定 ID、计算口径、统计窗口、红线阈值、阈值依据、击穿后果、响应动作和责任人。阈值优先依据法规／合同、产品承诺、历史分布或实验结果；没有依据时写“待验证，暂不设置确定红线”，不得编造数字。

涉及 AI 时再判断 AI 属于增效、赋能或决策价值模式，并从对应失败出发选择信号：

- 增效型：不能让用户采用后总耗时或成本反而增加；
- 赋能型：不能让用户生成了结果却无法真正使用；
- 决策型：不能让高风险错误被用户相信并采用。

AI 指标池只是候选。幻觉率、总体准确率或生成成功率是否为底线，取决于它是否直接对应本产品不可接受失败，不能按产品类型机械指定。

再列出 2 个伪底线指标，说明它为什么不是真底线、适用时属于哪类诊断指标，以及应关注的替代信号。底线通过失败对应性、提前发现能力、可复算性、阈值依据、子群体风险、制衡作用和响应责任门禁后，向用户确认。

用户确认后第三次更新同一文档，加入底线、伪底线、测量与行动契约、状态和证据。全部门禁通过时标为 `confirmed`；存在数据、基线、阈值或责任缺口时交付 `draft`，明确缺口影响。

## 信息与状态纪律

始终区分：

- `已确认`：用户确认，且口径、来源和责任边界可执行；
- `建议方案`：根据价值链推导，等待业务或数据验证；
- `待建立基线`：定义成立但没有历史分布；
- `待验证阈值`：红线或目标尚无事实依据；
- `分析推断`：根据相似产品机制形成，并非对方公开事实；
- `待确认冲突`：指标会诱导与产品价值或其他指标冲突的行为。

产品定义为 `confirmed` 不代表指标体系自动为 `confirmed`。不得编造业务数据、行业基准、对方北极星指标或红线阈值。

## 自动增量交付

三次阶段确认后均调用 `$document-publisher`，直接创建或更新同一最终门户正文：

1. 使用稳定文件 `docs/Product-Metrics-{product-slug}.mdx` 和同名 `.portal.json`；
2. 使用 `type: Product-Metrics`、`collection: 产品文档`、`layout: report`、`slug: {product-slug}-metrics`；
3. 优先写入上游 `PRODUCT_DEFINITION` 所在门户，并在正文记录上游 artifact 与路由；
4. 复用相同 slug 更新，不创建三份文档，不覆盖门户中的其他文档；
5. 每次写入后从实际路由读回，核验标题、阶段、主要指标、公式、门禁、状态和 presentation；
6. 未开始的章节不写空标题或空表格。

自动更新不等于自动启动服务。只有用户要求预览、打开或启动时才启动本地服务。用户明确要求仅在对话中输出、不要写入门户或指定其他交付方式时，按其要求缩减交付。

## 下游复用契约

下游任务可以把 `已确认` 的主要指标、过程指标、底线指标和测量口径作为基线，但不得把建议阈值、待建立基线或分析推断当作事实。埋点、数据建模、看板和实验设计必须引用稳定指标 ID；新证据改变口径时，显式更新版本和受影响项。
