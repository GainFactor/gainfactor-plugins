# 门户文档表达决策框架

本框架帮助内容 Skill 把业务材料组织成可扫描、可深入、可核验的门户文档。它不规定报告章节，也不替内容 Skill判断业务结论。

本框架中的 `fallback` 或“Markdown 降级”只描述同一份最终 `.mdx` 内的语法回退：富组件不可用时改用标准 Markdown 表格、列表或正文。不得因此创建独立 `.md`、中间稿或 Markdown→MDX 转换流程。

## 1. 先定义阅读任务

在选择组件前，用一句话回答：读者看完这一段要完成什么？常见任务包括：

| 阅读任务 | 优先表达 |
|-|-|
| 快速获取少量关键判断 | 短正文、`Callout`；确有首屏价值时用 presentation `metrics` |
| 精确核对字段、数值或差异 | Markdown 表格或 `TypeTable` |
| 比较少量同构对象 | 表格；需要先浏览对象概貌时用 `Cards` |
| 在互斥视角之间切换 | `Tabs` |
| 理解操作、阶段或时间顺序 | `Steps`；关系复杂时用 Mermaid 或 Infographic sequence |
| 理解层级、依赖、状态或传播路径 | Mermaid；少量简单节点可用 `NodeGraph` |
| 理解抽象格局、主次关系或视觉叙事 | AntV Infographic |
| 查看界面、图像或原始证据 | `ImageZoom` 配说明、来源及正文结论 |
| 识别风险、限制或前置条件 | `Callout`，不能只依靠颜色表达严重程度 |
| 辅助识别标题、状态、步骤或关键概念 | Lucide `Icon` 配合可见文字；图标不单独承担结论 |
| 先认识一个主体，再阅读字段和背景 | `Profile`；没有主体叙事时不要使用 |
| 扫描多组字段和值 | `InfoGrid`；精确横向比较仍用表格 |
| 阅读连续步骤及每步的结构化信息 | `StructuredSteps`；分支和回路用 Mermaid |
| 重复阅读多个同构内容单元 | `ContentPanel`；长篇连续论证保留正文 |
| 按多个并列分组浏览同构条目 | `GroupedBoard`；需要精确交叉比较时仍用表格 |

如果无法说清读者任务，先保留正文，不选择富组件。

## 2. 再识别信息关系

组件表达的是关系，不是文档类型。不要因为内容叫“竞品分析”“PRD”或“用户画像”就固定选某种图。

| 信息关系 | 适合的工具 | 不适合的情况 |
|-|-|-|
| 连续论证、上下文和限制条件 | Markdown | 不要切成大量孤立卡片 |
| 精确比较、多字段矩阵 | Markdown 表格 | 不要用信息图替代需逐格核验的数据 |
| 2–6 个同构对象 | `Cards` | 对象过多或字段过密时改用表格 |
| 同一主题的互斥视图 | `Tabs` | 内容需要同时对照时不要折叠进 Tab |
| 严格线性步骤 | `Steps` | 存在分支、回路或多主体交互时改用 Mermaid |
| 节点、边、分支、时序、状态 | Mermaid | 仅有三四条概念摘要时可能过重 |
| 少量简单有向节点 | `NodeGraph` | 复杂拓扑、时序和多种边语义优先 Mermaid |
| 摘要、阶段、层级、对比或故事化关系 | AntV Infographic | 精确数据、完整证据和复杂技术拓扑 |
| 一张需查看细节的图片 | `ImageZoom` | 多图证据集不应伪装成连续正文 |
| 结论、风险、边界 | `Callout` | 普通段落不要全部高亮 |

## 3. 设计阅读层级

一份报告化门户文档通常包含三种层级，但只使用实际需要的层级：

1. **定位层**：标题、范围、更新时间、适用对象，让读者知道文档解决什么问题。
2. **决策层**：少量关键判断、差异或路径，帮助读者快速决定先读哪里；可由 presentation manifest 或正文首段承担。
3. **证据层**：方法、事实、截图、比较表和限制，支持追溯与复核。

不要在三层重复相同文字。首屏模块只压缩正文已有信息，并通过标题或锚点把读者带向证据层。

## 4. 形成页面蓝图

写正文前，为真正影响阅读体验的章节记录一次选择。普通段落无需逐段登记。

```yaml
presentationDecision:
  audience: 产品决策者
  readerTasks:
    - 五分钟内理解主要差异
    - 能回到证据核验判断
  readingPath: executive-first
  sections:
    - id: landscape
      purpose: 建立对象之间的相对位置
      relation: comparison
      density: medium
      expression: infographic
      reason: 位置和分组比连续文字更容易扫读
      fallback: 二维比较表加分组小结
    - id: evidence
      purpose: 核验功能差异及证据
      relation: evidence
      density: high
      expression: table
      reason: 需要逐项核对并保留来源
      fallback: markdown-list
```

页面蓝图不是门户运行时 schema，也不要求发布。它是内容 Skill 写作时的决策协议。

## 5. AntV Infographic 的选择方法

只有当内容需要视觉叙事且表格、Mermaid 或普通组件不能更直接表达时，才进入 AntV 模板选择：

1. 从信息关系确定模板族：顺序用 `sequence`，对比用 `compare`，层级用 `hierarchy`，对象关系用 `relation`，摘要集合用 `list`。
2. 根据数据结构选择具体模板，而不是根据审美随机选择。
3. 读取 `antv-infographic-syntax.md`，只使用其中存在的模板和字段。
4. 确认每个节点有简短标签，详细证据仍留在正文。
5. 在页面蓝图中写明同一最终 `.mdx` 内的标准 Markdown 回退方式。

同一张图表达一种主要关系。若同时出现精确比较、复杂流程和结论摘要，应拆成正文表格、流程图和摘要，而不是塞进一张信息图。

## 6. 组合与版面节奏

- 一个视觉块前应有一句“为什么看它”，后面应有结论或证据入口。
- 连续两个视觉块必须承担不同阅读任务；否则合并或删除一个。
- 表格负责精确，图形负责关系，正文负责解释；三者不要机械复述。
- Cards 用于建立对象入口，不用于承载长篇分析。
- Tabs 只隐藏互斥内容，不隐藏读者必须连续阅读的论证。
- 截图必须带可辨识的 alt、说明和来源语境；单图可用 `ImageZoom`，多图能力未注册时采用带标题的小节，不编造 Gallery 组件。
- 组件在移动端失去可读性时，优先换成表格、列表或分节正文。
- 图标用于补充文字识别，不代替标题、状态文字、证据或关系图；同一语义在同一文档中保持同一图标。

## 7. 完成前检查

逐项确认：

- 每个富组件都能对应一个明确阅读任务和信息关系。
- 关键事实、限制和来源在不渲染富组件时仍可获得。
- 图表没有代替精确证据，首屏没有创造正文之外的新结论。
- 没有连续堆叠卡片、Callout 或信息图来制造“丰富感”。
- 所有组件与字段均在能力注册表中标记为 `registered`。
- 不支持的能力已经在同一最终 `.mdx` 内使用标准 Markdown 回退，或登记为能力缺口。
