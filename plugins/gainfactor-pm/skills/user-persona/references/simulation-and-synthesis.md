# 虚拟用户探索与归纳协议

## 1. 建立隔离 Agent

通常创建 4–6 个 Agent。每个 Agent 只获得自己的现实身份、当前事件、目标、资源、偏好、经验、关系、风险、失败后果和替代结果；不得看到产品定位、功能、候选用户画像、其他 Agent 或预期结论。

### 通用人物设定

- 姓名、年龄、学历、职业、常住地区；
- 家庭、同行或协作关系；
- 可支配时间、预算或其他关键资源；
- 性格特征、决策习惯、风险态度、工具熟悉度；
- 与当前领域有关的经验、偏好和反感；
- 当前具体事件、目标、限制、决策期限、失败后果和替代结果。

领域字段根据产品实际选择。旅行场景可以包含出发地、时间、预算、同行人、目的地和景观偏好；办公、金融、教育等场景必须换成对应对象。具体案例只用于本次模拟，不得写成跨领域固定要求。

MBTI 可作为人物行为一致性的辅助变量，但不能直接推导需求、偏好或画像分类。任何行为仍须由现实背景、任务、资源、经验、关系和风险解释。

### 真实性门禁

启动模拟前逐人检查：

1. **完整**：身份、事件、目标、资源、限制和风险齐备；
2. **现实一致**：时间、地点、预算、能力和选择没有明显矛盾；
3. **具体**：存在明确事件、行动对象和决策期限；
4. **可解释**：预期行为能从人物背景和习惯说明原因；
5. **有代表性**：体现可复现的需求和行为，不为某项功能临时拼接；
6. **不刻板**：年龄、性别、职业、学历和 MBTI 不直接决定需求；
7. **有差异**：Agent 之间至少在目标、方法、风险、信任或退出路径上存在实质不同。

任一项失败先修正人物设定，不运行盲测。

## 2. 无产品盲测

提供具体触发情境，不介绍产品。让 Agent 用第一人称逐步还原真实行动，而不是给出概括性流程。

每个行为 Step 按实际适用信息记录：

```yaml
step:
  trigger: 为什么进入这一步
  goal: 想确认或完成什么
  toolOrChannel: 使用的软件、工具、渠道、人物或现实方法
  usage: 如何使用，包括操作、输入、搜索、询问或比较方式
  object: 操作、查看、询问或比较的具体对象
  feedback: 得到了什么信息、结果或他人反馈
  interpretation: 用户怎样理解该反馈
  concern: 此时产生或保留的顾虑
  decision: 做出了什么判断
  nextAction: 下一步是什么及为什么
```

工具、品牌、搜索词、地点和对象必须来自人物的真实场景；没有使用软件时记录线下、电话、朋友、纸笔或经验等实际方法，不为追求具体而编造数字工具。示例内容不构成固定方案。

### 行为路径门禁

每名 Agent 必须有：明确触发、具体目标、实际行动、合理工具或方法、具体使用方式、获得的反馈、对反馈的判断、顾虑、下一步选择，以及失败、替代或放弃结果。只有“搜索—比较—选择”等抽象标签视为失败，必须补充追问。

所有 Agent 的盲测和原始回答保存后，才能进入产品测试。

## 3. 分命题测试

一次只展示一个中性最小产品命题。逐项询问并记录：

- 第一反应；
- 是否改变原有选择；
- 会在原路径的哪一步使用，以及如何使用；
- 产品给出什么反馈，用户怎样判断；
- 解决了原路径中的什么问题；
- 新增或保留了什么顾虑；
- 什么情况下继续、退出或回到原有方法；
- 最终态度及原因。

不得说服 Agent，不得根据回答临时补功能。

### 产品反馈门禁

反馈必须建立在完整当前路径上，明确产品介入步骤、行为是否变化、价值来源和真实顾虑；允许拒绝、无需求和保留原方案。不能回到人物背景或原路径的结论不得进入画像。

## 4. 建立工作证据

把人物设定、原始回答、每个 Step、命题反馈和门禁状态写入 research sidecar。缺失信息保留为空，不补写。正式报告只呈现产品判断所需内容，不展示完整模拟过程。

## 5. 选择目标用户

比较：使用背景、核心目标、期望结果、当前行为、工具与方法、核心痛点、决策与信任因素、产品前后变化、退出路径和期望能力。

候选画像需同时满足：

- 去掉产品后仍成立；
- 能解释稳定需求与行为，而非一次偶然事件；
- 与其他画像在目标、方法、风险、信任或行为变化上有产品意义的差异；
- 不依赖人口属性、MBTI、任务阶段或产品接受程度成立；
- 产品确实可能改变其行为或结果。

通常形成 3–5 个画像；证据不足时更少，不凑数。人物姓名、稳定身份、当前需求状态与现实限制分别写入 `PersonaBrief.name`、`PersonaBrief.identity` 和 `PersonaBrief.situation`；人物章节标题只使用“n 人物姓名”，避免抽象四字标签、广告文案和具体案例式群体命名。

## 6. 形成单个用户画像

按 `persona-schema.md` 逐人完成。人物背景、典型情境、核心目标、行为路径、痛点、决策与信任因素必须先稳定；之后才能推导期望产品功能和生成人物图片。单个画像通过门禁后立即写入最终 MDX，再处理下一个人物。

## 7. 综合需求与功能优先级

所有画像完成后才归纳：

- **共性问题**：至少由两个画像支持，表现可以不同但底层问题一致；
- **特殊问题**：明确对应人物、成立条件及是否影响公共流程；
- **P0**：缺少后核心用户无法完成主要任务或获得核心价值；
- **P1**：核心流程成立后显著改善体验或满足重要用户关键需求；
- **P2**：提高效率、覆盖、个性化或持续价值；
- **暂不纳入**：价值不足、风险过高、前置条件未成立或超出产品责任。

每项功能沿以下链路回溯：

`人物 → 使用背景 → 当前行为与反馈 → 痛点或信任问题 → 期望结果 → 服务能力 → 优先级理由 → 依赖与风险`

排序前先归一化功能：

1. 为每个人物的功能机会保留来源人物、来源步骤、解决的问题、服务能力、期望结果、顾虑和风险；
2. 只有“解决的问题”和“服务能力”实质相同时才合并，名称相似但介入行为不同的不合并；
3. 合并项使用稳定 `feature_id`，保留每个人物不同的优先程度、成立条件和顾虑，不用统一描述覆盖差异；
4. 同一问题需要不同能力时拆开，同一能力服务不同问题时分别说明价值来源；
5. 完成去重、合并和冲突检查后再判断 P0/P1/P2/暂不纳入。

P0/P1/P2 是用户价值优先级，不代表研发排期或交付承诺。
