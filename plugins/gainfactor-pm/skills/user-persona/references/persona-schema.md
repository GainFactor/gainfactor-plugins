# 用户画像结构

每个保留目标用户对应一个完整画像。画像用于帮助产品负责人和产品经理理解一个具体的人如何产生需求、采取行动、形成判断并期待产品提供帮助；不能把多个互相矛盾的经历拼成理想人物。

## 人物名称与定位

人物姓名直接写入 `PersonaBrief.name`，职业或稳定身份写入 `PersonaBrief.identity`，当前需求状态和现实限制写入 `PersonaBrief.situation`。每个人物先使用“n 人物姓名”格式的三级 `SectionHeading` 建立清晰的人物章节和目录入口，并在模块二内从 `1` 连续编号；随后紧接对应 `PersonaBrief`。人物标题只写编号与姓名，不使用抽象四字标签、宣传口号或偶然经历。

## 1. 人物背景

先展示人物图片和结构化基本信息，再写连续背景。通用字段包括：

- 姓名；
- 年龄；
- 学历；
- 职业；
- 常住地区；
- 性格特征；
- 可选 MBTI；
- 与当前需求确实相关的生活、工作、家庭或领域偏好。

背景正文说明人物近期处境、为什么现在产生需求、有什么资源与限制，以及哪些经验影响其选择。人口信息和 MBTI 只能帮助人物具体，不能直接解释需求。领域字段按产品实际选择，不把某个旅行、办公或金融案例固化为标准。

正式报告使用 `PersonaBrief` 把照片、姓名、稳定身份、用户优先级、当前处境、关键特征和必要短事实组织成人物章节导读：

- 人物前置的三级 `SectionHeading` 使用稳定锚点和“n 人物姓名”标题；`PersonaBrief` 不承担目录入口；
- `name` 写姓名；
- `role` 写职业或与本次研究直接相关的稳定身份；
- 用户优先级写入 `priority`，影响行为和选择的特征写入 `traits`；
- `summary` 写当前需求状态与现实限制，不写口号或人物标签；
- `image` 使用已经通过一致性检查的人物图片；
- `facts` 只写年龄、学历、地区和确实相关的短资料；`identity` 已写职业时不再重复；
- 典型情境、核心目标、关键约束和可接受替代结果进入后续独立分节，不塞入横向事实区；
- `traits` 只写有助于理解当前行为的偏好、约束或习惯；
- `PersonaBrief` 之后使用“人物背景”四级标题和背景正文；后续依次使用“典型情境”“核心目标”“关键行为与核心痛点”“决策与信任关键”“期望产品功能”。

`PersonaBrief` 只承担快速认识人物，不承载完整背景、行为路径、痛点和功能说明。不得在其前后重复同一张照片、姓名或基础资料。没有图片时允许无图布局；不得插入空路径。

## 2. 典型情境

用一个真实故事片段说明：

- 什么事件在什么时间触发需求；
- 当时环境、任务对象与参与者；
- 已知限制、决策期限和失败后果；
- 人物已经考虑或采取了什么行动。

具体地点、工具、商品、文件、人物或搜索内容必须与本次领域和人物设定一致；具体不是堆品牌，而是让后续行为可以被理解和复核。

## 3. 核心目标（JTBD）

分别写：

- **核心任务**：人物在该情境下真正要完成什么；
- **期望结果**：完成后希望得到什么可观察结果；
- **必须满足的条件**：哪些条件缺失就不算完成；
- **可接受的替代结果**：无法完成时会退到哪里。

## 4. 关键行为与核心痛点

### 当前行为路径

按连续 Step 还原行为。每个 Step 按实际适用信息包含：

- 目标；
- 工具、软件、渠道、人物或现实方法；
- 使用方式，包括输入、搜索、询问、查看、比较或操作；
- 操作对象；
- 获得的反馈；
- 用户对反馈的理解；
- 当前顾虑；
- 决定与下一步。

如果没有使用工具，不得强行补工具；如果产品领域需要具体软件、搜索词、地点或对象，必须写清楚，但任何具体案例都不能成为所有画像的标准答案。

正式报告使用 `Steps/Step`。每个步骤的 `title` 写当前任务或行为阶段，`content` 写实际行动，`fields` 按本次情境映射工具或方法、使用方式、对象、反馈、判断、顾虑、决定和下一步。没有发生的字段省略，不能为了视觉整齐补造信息。

### 核心痛点

只从上述行为路径提炼。每个痛点说明：发生在哪一步、用户做了什么、得到了什么反馈、为什么没有继续，以及产生什么结果。不得跳过路径直接生成通用痛点。

## 5. 决策与信任关键

说明：

- 决策因素；
- 信任因素；
- 最担心的 1–2 件事；
- 什么情况下继续；
- 什么情况下放弃；
- 什么情况下回到原有方法。

所有判断必须能回到人物背景、典型情境或当前行为中的具体反馈。

## 6. 期望产品功能

每项功能独立成节，不使用功能矩阵压缩叙事。固定说明：

1. **服务能力**：产品需要提供什么服务；
2. **对应需求**：来自人物的哪个目标、行为、反馈或痛点；
3. **解决的问题**：准备改变当前路径中的什么；
4. **期望结果**：用户使用后可以获得什么结果；
5. **核心顾虑**：人物对该能力最担心什么；
6. **依赖条件与潜在风险**：确实存在时再写，不为完整而编造。

功能必须沿“背景 → 情境 → 行为 → 反馈 → 痛点或信任问题 → 期望能力”推导，不得从通用产品经验直接生成。

正式报告每项功能使用一个 `Panel`：标题写功能名称，说明写服务能力，字段区写对应需求、解决的问题和期望结果，正文补充推导依据，提示区只在确有核心顾虑、依赖或风险时使用。组件标签可以写主要服务人物，但不能用标签替代正文中的来源说明。

## 画像内容门禁

- 人物信息完整，背景具体、现实且不依赖刻板印象；
- 典型情境包含真实事件、限制、期限和结果；
- 核心任务、期望结果和替代结果清楚；
- 每个 Step 具有实际行动、方法、反馈、顾虑和下一步；
- 痛点来自路径，决策与信任来自背景和反馈；
- 每项期望产品功能能回到前文，并说明服务能力、问题、结果和顾虑；
- 没有抽象标签、研究黑话、营销口号或为了具体而堆砌无关案例；
- 与其他画像在产品需要处理的目标、行为、风险或信任上有实质差异。

内容门禁通过后才能生成人物图片，不得要求尚未生成的图片参与本门禁。

## 人物导读与表达门禁

- 图片与年龄感、生活状态、环境和情境一致；
- PersonaBrief 已将照片、身份、优先级、当前处境、关键特征和短事实组织成人物导读，`identity` 与 `facts` 没有重复职业或其他资料；
- 人物三级标题承担目录入口，PersonaBrief 紧随其后且不重复编号；导读没有把后文整段复制进来；
- 短事实桌面端最多两列，移动端和打印视图为单列；
- Steps/Step 中每一步的行动与字段可以连续读懂；
- Panel 中每项功能可以回到前文来源；
- 人物内部标题带对应姓名并形成唯一锚点，不与其他人物的小节冲突；
- PersonaBrief 图片 alt 唯一，首屏卡片可以通过同一 alt 解析图片。
- 每个人物具有独立三级章节标题，人物背景与典型情境、核心目标等内容具有一致的四级标题层级；相邻人物之间存在清晰章节边界。
- 人物的普通数字编号与 G5 冻结顺序一致；人物内部标题不编号，目录与正文完全一致。
- 当前人物从 PersonaBrief 到全部期望产品功能连续闭合，下一人物开始前没有遗漏；人物块内没有其他人物的姓名、persona_id、图片 alt、功能或来源。
- PersonaBrief traits 只保留会影响当前行为或选择的偏好、约束和决策习惯；功能标签只写主要服务人物或确有区分度的需求类别。

通过后立即写入正式报告，再处理下一个画像。
