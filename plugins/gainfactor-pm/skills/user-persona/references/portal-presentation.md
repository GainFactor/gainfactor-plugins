# User Persona 门户呈现

门户首屏只服务模块一“产品定义与目标用户”，帮助产品负责人快速理解产品、用户选择和人物概览。它不重复模块二的完整画像，也不提前展示模块三的完整路线图。

在写作阶段调用 `$document-publisher` 形成页面蓝图并直接写最终 MDX。全文结论稳定后，在报告同目录完成同名 `.portal.json`，使用 Portal Presentation v1 和 `layout: report`。

## 推荐模块

### 产品定义：`callout`

只放一条能够独立说明“产品在什么背景下为用户提供什么帮助”的核心定义。页面标题使用“产品定义”，不出现组件名称。

### 核心结论：`metrics`

使用 3–6 项正文已有判断，例如首先服务谁、同样重要的用户、产品首先解决什么和最高影响的验证问题。值保持简短；不放 Agent 数量、研究方法或无法脱离正文理解的缩写。

### 用户画像概览：`cards`

每个已通过门禁的用户画像一张卡：

- `title`：人物姓名；
- `eyebrow`：使用背景或需求类别，不用抽象四字标签；
- `description`：具体使用背景；
- `fields`：核心目标、期望结果、用户优先级；
- 图片：正文图片来自 `Profile.image`；卡片的 `sourceImageAlt` 填写对应 `Profile.image.alt`。由 `$document-publisher` 在导入后解析并写入门户资产 URL；本 Skill 不重复插入 Markdown 图片，也不预测门户资产路径。

不强制 `quote`；报告未保留有价值且自然的原话时省略。卡片不放完整人口信息、行为路径、痛点、功能、Agent ID 或反馈索引。

## 不放入首屏

- 完整研究流程和 Agent 样本；
- 每个人物的详细路径；
- 完整共性与特殊问题；
- P0/P1/P2 功能详情与风险；
- 正文没有的新结论。

模块三的需求关系和功能优先级使用正文 `GroupedBoard`、必要的 Markdown 矩阵和解释文字表达，不重复进 Presentation。

## 写入与校验节奏

- 产品上下文通过后可以创建 `callout` 和 `metrics` 草稿；
- 每个画像完成后向 `cards` 草稿增加对应人物；
- 草稿不发布为最终清单；全部三模块完成并整体优化后再统一校验；
- `sourceImageAlt` 未解析、对应多个不同图片、人物卡缺姓名/定位/背景/核心目标/期望结果/优先级，或 manifest 引入正文外判断时阻断发布；
- 最终由 `$document-publisher` 校验，再交给 `$document-review` 挂载门户，不允许发布阶段补写业务内容。
