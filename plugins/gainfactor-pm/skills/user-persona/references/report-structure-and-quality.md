# USER_PERSONA 报告结构与质量门禁

`USER_PERSONA` 是面向产品负责人和产品经理的产品判断文档。读者应能快速理解产品、目标用户、每个具体人物，以及这些人物共同导出的功能优先级。研究方法、完整 Agent 记录和合并过程保存在 research sidecar，不占用主报告阅读路径。

## 写入与表达契约

- 默认直接生成最终 `.mdx`，不先写普通 Markdown 再让发布器猜测语义。
- 全文只有一个文档标题，正文只有三个主模块。标题编号直接写入标题文本：主模块使用中文序号 `一、`、`二、`、`三、`；每个主模块内的章节使用普通阿拉伯数字 `1`、`2`、`3`，并在进入新主模块时重新从 `1` 开始；人物内部固定章节不编号。不得使用 `1.1`、`2.1` 等复合编号，也不得只靠字号、缩进、CSS 计数器或目录样式表达层级。已注册 `SectionHeading` 时统一使用它，并配置稳定标题、语义层级、图标和锚点。模块二中人物使用三级“n 人物姓名”，人物背景及后续内容使用四级专业标题；门户右侧目录必须显示到人物内部这一层。
- 不生成手写目录。人物三级标题提供稳定评审入口，人物内部四级标题进入右侧目录；各人物使用带人物前缀的唯一锚点，避免同名“典型情境”“核心目标”等标题发生锚点冲突。
- 只使用 `$document-publisher` 能力注册表中 `registered` 的 Markdown、MDX 组件、Mermaid 和 Infographic；禁止任意 HTML、脚本、内联样式和未注册组件。
- PersonaBrief 负责人物章节导读，FieldList 负责紧凑字段，Steps/Step 负责过程，Panel 负责重复内容单元，Board 负责分组浏览，表格负责精确比较，正文负责解释。PersonaBrief 不包裹后续正文。
- 本地人物图片写入 `PersonaBrief.image` 并使用项目相对路径；图片 alt 包含人物姓名和可观察的使用背景。
- 具体案例、软件、搜索词、地点、对象和反馈只属于当前人物，不作为跨项目模板。
- `Artifact Type`、`Status`、`Research Mode` 等稳定元信息写入 `.portal.json`、门户发布参数或内部 sidecar，不用引用块、表格或正文段落在标题下重复展示；正文跟随用户语言。

## 视觉层级与语义装饰

图标和标签用于帮助扫描信息，不用于填满页面。

- 二级模块使用稳定图标：产品定义与目标用户使用 `compass`，用户画像使用 `users`，用户 × 功能优先级路线图使用 `route`。
- 承担导航作用的三级章节按语义选择稳定 Lucide 图标，例如产品定义 `badge-info`、目标用户选择 `user-round-check`、用户需求综合分析 `scan-search`、功能归一化 `git-merge`、功能优先级路线图 `milestone`、总结 `clipboard-check`、产品结论 `flag`。只有能力注册表确认图标和 `SectionHeading` 可用时才写入；不可用时保留标准 Markdown 标题，不用任意 HTML 模拟。
- 人物内部四级标题保持专业字段名称，不添加带圈数字；使用已注册的 `SectionHeading level={4}` 和语义图标，能力不可用时降级为同层级 Markdown 标题，不在标题前零散拼接 standalone Icon。
- 视觉字号必须服从文档语义层级：主模块标题大于人物标题，人物标题大于人物内部章节；Steps/Step 步骤名、Panel 功能名和 Board 条目名属于组件内部标题，字号与字重不得超过其所属章节标题。
- 章节编号是标题语义的一部分，正文与目录必须显示同一编号；新增、删除、合并或调整人物后，从前到后重新检查主模块中文序号和各主模块内从 `1` 开始的阿拉伯数字编号，不保留跳号、重号、复合编号或不同层级混用。
- PersonaBrief traits 只表达会影响行为或选择的稳定偏好、约束和决策习惯；Panel 与 Board 的分类信息写入正文或组合的 `FieldList`。
- 禁止使用“四类用户”“全部画像”“核心功能”等可以从上下文直接看出、无法区分条目的标签。优先级由分组或 eyebrow 表达，不在每个标签中重复 P0/P1/P2。
- 连续两个以上高密度组件时，用一个短段落说明接下来要看什么以及为什么重要；不得用空卡片、装饰性 callout 或重复结论制造间距。

## 页面蓝图

每个正式板块写入前先记录以下决策，蓝图保存在内部工作产物，不原样展示给读者：

| 板块 | 对读者的价值 | 信息关系 | 首选表达 | Markdown 降级 |
|-|-|-|-|-|
| 产品定义与目标用户 | 快速理解产品边界、目标用户和主要判断 | 摘要、选择 | 短正文、FieldList、首屏 cards | 正文、字段列表、人物入口列表 |
| 人物导读 | 先认识具体人物，再进入现实处境和行为分析 | 人物导读 | PersonaBrief | 图片、姓名、处境短文和事实列表 |
| 典型情境 | 理解需求如何被具体事件触发 | 连续叙事 | 正文 | 正文 |
| 核心目标 | 区分任务、结果、完成条件和替代结果 | 结构化字段 | FieldList | 定义列表 |
| 关键行为 | 看清连续行动、反馈和判断变化 | 顺序 | Steps/Step | 编号小节和字段列表 |
| 核心痛点 | 回到具体步骤理解受阻原因和后果 | 解释 | 短正文或 Panel | 分节正文 |
| 决策与信任 | 同时查看选择依据、信任条件和退出条件 | 条件分组 | FieldList 或并列正文 | 分组列表 |
| 期望产品功能 | 逐项理解服务能力、来源、结果和顾虑 | 同构内容单元 | Panel | 固定顺序的小节正文 |
| 共性与特殊问题 | 区分基础能力与条件性需求 | 分类 | Board | 两组标题和列表 |
| 功能优先级路线图 | 浏览优先级、人物来源、价值和风险 | 分组 | Board；另附精确矩阵时用表格 | 优先级标题和结构化列表 |

只有当实际信息关系与上表一致时使用相应组件。一个组件前后的正文负责解释其意义，不机械复述组件内字段。

## 一、产品定义与目标用户

本模块回答：产品解决什么问题，为什么选择这些用户，以及当前最重要的产品判断是什么。

### 核心结论

用少量结论说明：产品主要解决的问题、核心与重要用户、用户之间最重要的差异，以及当前最值得投入的产品方向。首屏 `metrics` 只压缩正文已经存在的 3–6 个判断，不显示 Agent 数量等研究过程信息。

### 产品定义

说明使用背景、用户需求、当前解决方式、产品提供的核心价值和产品能力边界。核心定义使用短正文，适合扫描的产品范围与约束使用 `FieldList`；只有产品介入关系比正文明显更清楚时才使用一张 Infographic。保持产品语言，不展示研究术语。

### 目标用户选择

说明形成了哪些画像、谁是核心或重要用户、选择依据和产品能产生的价值。“核心、重要、机会”表示本次产品判断，不代表人口规模。

### 用户画像概览

正文先用一个短段落列出保留人物、用户优先级和选择依据，姓名与模块二的 `PersonaBrief.name` 完全一致。Portal Presentation `cards` 在首屏提供带图快速入口，卡片以 `sourceImageAlt` 引用对应 `PersonaBrief.image.alt`，不为首屏重复插入正文图片。

## 二、用户画像

严格按 `persona-schema.md` 和 G5 人物顺序逐人书写。每个人物使用三级“n 姓名”建立章节边界；`PersonaBrief` 紧随人物标题，`name`、`identity`、`priority` 和 `situation` 分别表达姓名、稳定身份、用户优先级和当前处境。PersonaBrief 之后以“人物背景”四级标题进入正文。

### 人物背景

使用一个 `PersonaBrief` 形成简短的人物导读。左侧照片帮助读者建立人物与处境的视觉认识；右侧只展示姓名、稳定身份、用户优先级、当前处境、关键特征和必要短事实。典型情境、核心目标、关键约束和替代结果保留在后续独立分节，不挤入横向字段。

### 典型情境

用连续故事说明具体触发事件、时间、环境、任务对象、限制、期限和失败后果。普通正文优先，不把故事切成卡片。

### 核心目标（JTBD）

使用 `FieldList` 分别展示核心任务、期望结果、必须满足的条件和可接受替代结果。字段内容较长时跨列或整行；本节用于精确区分任务与结果，不使用醒目的警告或营销式卡片。

### 关键行为与核心痛点

用 `Steps/Step` 呈现连续行为。步骤标题写用户当前要完成的任务，主体写真实行动，字段按情境适用地展示工具或现实方法、使用方式、对象、反馈、判断、顾虑、决定和下一步；不能只有抽象标签。存在分支、回退或退出且线性步骤无法解释时才用 Mermaid。

痛点在路径之后逐项解释发生在哪一步、用户获得什么反馈、为何受阻及造成什么结果。少量痛点使用短正文；多个同构痛点需要反复核对来源时可以使用 `Panel`。不得从通用经验跳过路径生成痛点。

### 决策与信任关键

使用 `FieldList` 或两个并列正文区域说明决策因素、信任因素、主要担忧、继续条件、放弃条件和回到原方法的条件。字段较少或需要连续解释时保留正文；只有需要逐项精确比较时才使用表格。

### 期望产品功能

每项功能使用独立的 `Panel`，不使用功能矩阵压缩人物叙事：

- `title`：功能名称；
- `description`：产品应提供的服务能力；
- `fields`：对应需求、解决的问题和期望结果；
- `children`：来自人物背景、情境或行为步骤的推导依据；
- `notice`：确实存在时写核心顾虑、依赖或风险，否则省略。

多个功能保持相同字段顺序和视觉节奏。所有功能都必须能回到本人物前文。

## 三、用户 × 功能优先级路线图

本模块在所有画像完成后编写。

### 用户需求综合分析

使用 `Board` 分为“共性问题”和“特殊问题”。每个条目写问题、涉及人物、来源行为或情境、成立条件和产品影响；共性问题至少由两个画像支持，特殊问题明确具体人物和条件。两类内容需要同时比较，不放入 Tabs。需要精确核对人物覆盖关系时补充 Markdown 表格。

### 功能归一化

把各人物的功能机会按“解决的问题 + 服务能力”归一化。每个合并后的功能分配稳定 `feature_id`，记录原人物功能、来源步骤、合并理由、未合并的差异、各人物优先程度和顾虑。名称相近但介入行为不同的功能保持分开；归一化过程保存在 research sidecar，正文只解释会影响路线图理解的合并或分拆判断。

### 功能优先级路线图

- **P0**：缺少后核心用户无法完成主要任务或获得核心价值；
- **P1**：核心流程成立后显著改善体验，或满足重要用户的关键需求；
- **P2**：提高效率、覆盖、个性化或持续价值；
- **暂不纳入**：价值不足、风险过高、前置条件未成立或超出产品责任。

P0/P1/P2 是用户价值优先级，不是研发排期。使用 `Board` 按 P0、P1、P2、暂不纳入分组，每个条目写功能说明、服务人物、用户侧优先程度、来源问题以及确实存在的风险或依赖。分组文字必须独立表达含义，不依赖颜色；不得使用时间轴或阶段箭头暗示交付顺序。“暂不纳入”是本次判断，不默认表示未来必做。

### 功能详细说明（按需）

需要展开路线图中无法容纳的推导、依赖或风险时，再使用 `Panel` 逐项详细说明：

1. 功能名称与优先级；
2. 稳定 feature_id；
3. 功能说明；
4. 主要服务人物；
5. 各人物的用户优先级；
6. 来源需求；
7. 解决的问题；
8. 预期价值；
9. 依赖条件；
10. 确实存在的潜在风险。

风险可涉及技术、数据、安全、隐私、资金、合规、履约、信任或商业影响；没有则省略，不强行补齐。

### 总结

总结共性和特殊需求、首先需要解决的问题、人物差异、最大风险和下一步验证。

### 产品结论

明确优先服务谁、首先解决什么、核心价值是什么、当前不应承担什么，以及哪些问题会改变优先级。

## 专业语言规则

- 主模块和字段使用稳定产品语言，如“使用背景、核心目标、期望结果、决策与信任关键、期望产品功能”；副标题可补充具体解释。
- 人物内容先写具体事件、动作、反馈和结果，再归纳判断；不用定语加人称的水话。
- 避免抽象四字画像标签、研究黑话、营销口号和过度文案化标题。
- 每句话尽量说明谁在什么条件下做什么、得到什么反馈、为何这样判断及产生什么结果。
- 组件名只存在于 MDX 和 Skill 规则中，不能出现在页面文案。
- 示例只帮助理解字段，不得复制为其他领域或人物的标准内容。

## 最终质量门禁

### 内容

- 三个模块回答产品负责人和产品经理的核心问题；
- 没有不必要的研究流程、Agent 样本和原始反馈堆叠；
- 每个画像通过单独门禁并已逐个写入；
- 痛点来自路径，决策来自背景与反馈，功能来自需求与顾虑；
- 共性与特殊问题均能回到人物；
- 每项功能能回到人物姓名和具体来源，优先级理由成立；
- 跨人物功能已经归一化，每个路线图功能具有稳定 feature_id，合并没有覆盖人物差异；
- 模块一概览、模块二人物块、模块三人物引用和 Presentation cards 使用同一人物顺序；
- 每个人物内容连续闭合，没有其他人物的功能、姓名、persona_id、图片 alt 或来源混入；
- 没有根据未采集信息生成精确群体规模或比例。

### 语言

- 标题专业、稳定，副标题具体；
- 正文主模块使用中文序号、每个主模块内章节使用从 `1` 开始的普通阿拉伯数字、人物内部章节不编号；不出现带圈数字或 `1.1` 等复合编号，目录与正文标题完全一致，没有跳号、重号或仅靠样式表达的隐含层级；
- 没有抽象标签、研究黑话、营销文案或组件名称；
- 没有把具体案例当作通用规则；
- 人物足够具体，但所有细节彼此一致并与产品领域相关。

### 表达

- 每个富组件对应明确阅读任务；
- 每个板块已经说明其阅读价值、信息关系、组件映射和 Markdown 降级；
- 人物照片、身份、优先级、当前处境、关键特征和短事实构成一个 PersonaBrief；背景与分析正文位于其后的独立章节；
- 短字段在桌面端使用多列空间，移动端和打印状态仍保持可读；
- 图形、表格与正文没有机械重复；
- 每个 Step 包含真实行动、方法、反馈、顾虑和下一步；
- 功能机会使用 Panel 保持稳定结构，优先级使用 Board 分组且不暗示研发排期；
