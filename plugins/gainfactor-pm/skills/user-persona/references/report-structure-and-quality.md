# USER_PERSONA 报告结构与质量门禁

`USER_PERSONA` 是面向产品负责人和产品经理的产品判断文档。读者应能快速理解产品、目标用户、每个具体人物，以及这些人物共同导出的功能优先级。研究方法、完整 Agent 记录和合并过程保存在 research sidecar，不占用主报告阅读路径。

## 写入与表达契约

- 默认直接生成最终 `.mdx`，不先写普通 Markdown 再让发布器猜测语义。
- 全文只有一个一级标题，正文只有三个二级模块。人物姓名由 Profile 自身形成三级视觉标题，不在 Profile 前重复添加同名三级标题；人物内部使用“内容类别｜人物姓名”的四级标题，使目录锚点在多个人物之间保持唯一。
- 不生成手写目录。当前 Profile 未提供独立目录锚点时，以人物首个内部标题作为稳定评审入口；不得生成多个同名“典型情境”“核心目标”等标题。
- 只使用 `$document-publisher` 能力注册表中 `registered` 的 Markdown、MDX 组件、Mermaid 和 Infographic；禁止任意 HTML、脚本、内联样式和未注册组件。
- Profile 负责主体档案，InfoGrid 负责紧凑字段，StructuredSteps 负责过程，ContentPanel 负责重复内容单元，GroupedBoard 负责分组浏览，表格负责精确比较，正文负责解释。所谓 Markdown 降级，是指组件内文字不依赖颜色、图标或交互也能理解，并为不支持组件的目标格式提供等价写法；正式 MDX 不同时重复一份降级正文。
- 本地人物图片写入 `Profile.image` 并使用项目相对路径；图片 alt 包含人物姓名和可观察的使用背景。
- 具体案例、软件、搜索词、地点、对象和反馈只属于当前人物，不作为跨项目模板。
- `Artifact Type`、`Status`、`Research Mode` 等稳定元信息保持英文；正文跟随用户语言。

## 页面蓝图

每个正式板块写入前先记录以下决策，蓝图保存在内部工作产物，不原样展示给读者：

| 板块 | 对读者的价值 | 信息关系 | 首选表达 | Markdown 降级 |
|-|-|-|-|-|
| 产品定义与目标用户 | 快速理解产品边界、目标用户和主要判断 | 摘要、选择 | 短正文、InfoGrid、首屏 cards | 正文、字段列表、人物入口列表 |
| 人物背景 | 先认识具体人物，再理解资料和现实处境 | 主体档案 | Profile | 图片、四列表格、正文 |
| 典型情境 | 理解需求如何被具体事件触发 | 连续叙事 | 正文 | 正文 |
| 核心目标 | 区分任务、结果、完成条件和替代结果 | 结构化字段 | InfoGrid | 定义列表 |
| 关键行为 | 看清连续行动、反馈和判断变化 | 顺序 | StructuredSteps | 编号小节和字段列表 |
| 核心痛点 | 回到具体步骤理解受阻原因和后果 | 解释 | 短正文或 ContentPanel | 分节正文 |
| 决策与信任 | 同时查看选择依据、信任条件和退出条件 | 条件分组 | InfoGrid 或并列正文 | 分组列表 |
| 期望产品功能 | 逐项理解服务能力、来源、结果和顾虑 | 同构内容单元 | ContentPanel | 固定顺序的小节正文 |
| 共性与特殊问题 | 区分基础能力与条件性需求 | 分类 | GroupedBoard | 两组标题和列表 |
| 功能优先级路线图 | 浏览优先级、人物来源、价值和风险 | 分组 | GroupedBoard；另附精确矩阵时用表格 | 优先级标题和结构化列表 |

只有当实际信息关系与上表一致时使用相应组件。一个组件前后的正文负责解释其意义，不机械复述组件内字段。

## 一、产品定义与目标用户

本模块回答：产品解决什么问题，为什么选择这些用户，以及当前最重要的产品判断是什么。

### 核心结论

用少量结论说明：产品主要解决的问题、核心与重要用户、用户之间最重要的差异，以及当前最值得投入的产品方向。首屏 `metrics` 只压缩正文已经存在的 3–6 个判断，不显示 Agent 数量等研究过程信息。

### 产品定义

说明使用背景、用户需求、当前解决方式、产品提供的核心价值和产品能力边界。核心定义使用短正文，适合扫描的产品范围与约束使用 `InfoGrid`；只有产品介入关系比正文明显更清楚时才使用一张 Infographic。保持产品语言，不展示研究术语。

### 目标用户选择

说明形成了哪些画像、谁是核心或重要用户、选择依据和产品能产生的价值。“核心、重要、机会”表示本次产品判断，不代表人口规模。

### 用户画像概览

正文先用一个短段落列出保留人物、用户优先级和选择依据，姓名与模块二的 `Profile.name` 完全一致；保证不加载 Presentation 时仍能理解目标用户选择。Portal Presentation `cards` 在首屏提供带图快速入口，每张卡只显示姓名、人物定位、使用背景、核心目标、期望结果和用户优先级；完整字段留在模块二。卡片以 `sourceImageAlt` 引用对应 `Profile.image.alt`，由发布器解析门户资产路径，不为首屏重复插入正文图片。

## 二、用户画像

严格按 `persona-schema.md` 逐人书写。Profile 的 `name` 使用人物姓名，`role` 使用职业或稳定身份，`summary` 补充当前需求状态与现实限制；不另写文案式人物标题。人物内部 Markdown 标题统一写成“内容类别｜人物姓名”，既保持专业字段名称，也避免跨人物锚点重复。

### 人物背景

使用一个 `Profile` 形成完整人物档案，而不是依次堆放图片、表格和正文。左侧照片帮助读者建立人物与处境的视觉认识；右侧依次展示姓名、职业或稳定身份、当前需求状态、多列基础资料和领域偏好；背景正文说明近期事件、资源、限制和已有经验。短字段由 Profile 内部的 InfoGrid 在桌面端自动形成三至四列，移动端降为一列。没有充分信息的字段省略，不为了完整编造，也不在组件外重复资料。

### 典型情境

用连续故事说明具体触发事件、时间、环境、任务对象、限制、期限和失败后果。普通正文优先，不把故事切成卡片。

### 核心目标（JTBD）

使用 `InfoGrid` 分别展示核心任务、期望结果、必须满足的条件和可接受替代结果。字段内容较长时跨列或整行；本节用于精确区分任务与结果，不使用醒目的警告或营销式卡片。

### 关键行为与核心痛点

用 `StructuredSteps` 呈现连续行为。步骤标题写用户当前要完成的任务，主体写真实行动，字段按情境适用地展示工具或现实方法、使用方式、对象、反馈、判断、顾虑、决定和下一步；不能只有抽象标签。存在分支、回退或退出且线性步骤无法解释时才用 Mermaid。

痛点在路径之后逐项解释发生在哪一步、用户获得什么反馈、为何受阻及造成什么结果。少量痛点使用短正文；多个同构痛点需要反复核对来源时可以使用 `ContentPanel`。不得从通用经验跳过路径生成痛点。

### 决策与信任关键

使用 `InfoGrid` 或两个并列正文区域说明决策因素、信任因素、主要担忧、继续条件、放弃条件和回到原方法的条件。字段较少或需要连续解释时保留正文；只有需要逐项精确比较时才使用表格。

### 期望产品功能

每项功能使用独立的 `ContentPanel`，不使用功能矩阵压缩人物叙事：

- `title`：功能名称；
- `description`：产品应提供的服务能力；
- `fields`：对应需求、解决的问题和期望结果；
- `children`：来自人物背景、情境或行为步骤的推导依据；
- `notice`：确实存在时写核心顾虑、依赖或风险，否则省略。

多个功能保持相同字段顺序和视觉节奏。所有功能都必须能回到本人物前文。

## 三、用户 × 功能优先级路线图

本模块在所有画像完成后编写。

### 用户需求综合分析

使用 `GroupedBoard` 分为“共性问题”和“特殊问题”。每个条目写问题、涉及人物、来源行为或情境、成立条件和产品影响；共性问题至少由两个画像支持，特殊问题明确具体人物和条件。两类内容需要同时比较，不放入 Tabs。需要精确核对人物覆盖关系时补充 Markdown 表格。

### 功能归一化

把各人物的功能机会按“解决的问题 + 服务能力”归一化。每个合并后的功能分配稳定 `feature_id`，记录原人物功能、来源步骤、合并理由、未合并的差异、各人物优先程度和顾虑。名称相近但介入行为不同的功能保持分开；归一化过程保存在 research sidecar，正文只解释会影响路线图理解的合并或分拆判断。

### 功能优先级路线图

- **P0**：缺少后核心用户无法完成主要任务或获得核心价值；
- **P1**：核心流程成立后显著改善体验，或满足重要用户的关键需求；
- **P2**：提高效率、覆盖、个性化或持续价值；
- **暂不纳入**：价值不足、风险过高、前置条件未成立或超出产品责任。

P0/P1/P2 是用户价值优先级，不是研发排期。使用 `GroupedBoard` 按 P0、P1、P2、暂不纳入分组，每个条目写功能说明、服务人物、用户侧优先程度、来源问题以及确实存在的风险或依赖。分组文字必须独立表达含义，不依赖颜色；不得使用时间轴或阶段箭头暗示交付顺序。“暂不纳入”是本次判断，不默认表示未来必做。

### 功能详细说明（按需）

需要展开路线图中无法容纳的推导、依赖或风险时，再使用 `ContentPanel` 逐项详细说明：

1. 功能名称与优先级；
2. 稳定 feature_id；
3. 功能说明；
4. 主要服务人物；
5. 各人物的用户优先级；
6. 来源需求；
7. 解决的问题；
8. 预期价值；
9. 依赖条件；
10. 确实存在的潜在风险。

风险可涉及技术、数据、安全、隐私、资金、合规、履约、信任或商业影响；没有则省略，不强行补齐。

### 总结

总结共性和特殊需求、首先需要解决的问题、人物差异、最大风险和下一步验证。

### 产品结论

明确优先服务谁、首先解决什么、核心价值是什么、当前不应承担什么，以及哪些问题会改变优先级。

## 专业语言规则

- 主模块和字段使用稳定产品语言，如“使用背景、核心目标、期望结果、决策与信任关键、期望产品功能”；副标题可补充具体解释。
- 人物内容先写具体事件、动作、反馈和结果，再归纳判断；不用定语加人称的水话。
- 避免抽象四字画像标签、研究黑话、营销口号和过度文案化标题。
- 每句话尽量说明谁在什么条件下做什么、得到什么反馈、为何这样判断及产生什么结果。
- 组件名只存在于 MDX 和 Skill 规则中，不能出现在页面文案。
- 示例只帮助理解字段，不得复制为其他领域或人物的标准内容。

## 最终质量门禁

### 内容

- 三个模块回答产品负责人和产品经理的核心问题；
- 没有不必要的研究流程、Agent 样本和原始反馈堆叠；
- 每个画像通过单独门禁并已逐个写入；
- 痛点来自路径，决策来自背景与反馈，功能来自需求与顾虑；
- 共性与特殊问题均能回到人物；
- 每项功能能回到人物姓名和具体来源，优先级理由成立；
- 跨人物功能已经归一化，每个路线图功能具有稳定 feature_id，合并没有覆盖人物差异；
- 没有根据未采集信息生成精确群体规模或比例。

### 语言

- 标题专业、稳定，副标题具体；
- 没有抽象标签、研究黑话、营销文案或组件名称；
- 没有把具体案例当作通用规则；
- 人物足够具体，但所有细节彼此一致并与产品领域相关。

### 表达

- 每个富组件对应明确阅读任务；
- 每个板块已经说明其阅读价值、信息关系、组件映射和 Markdown 降级；
- 人物照片、资料和背景构成一个 Profile，没有图片与两列表格割裂或重复；
- 短字段在桌面端使用多列空间，移动端和打印状态仍保持可读；
- 图形、表格与正文没有机械重复；
- 每个 Step 包含真实行动、方法、反馈、顾虑和下一步；
- 功能机会使用 ContentPanel 保持稳定结构，优先级使用 GroupedBoard 分组且不暗示研发排期；
- 组件内容不依赖颜色、图标或交互才能理解；需要其他格式时存在明确的 Markdown 等价写法，正式 MDX 没有重复降级正文；
- 页面只使用已注册能力，桌面端和移动端均可阅读。

### 发布

- `.mdx`、图片和 `.portal.json` 均存在并通过对应校验；
- Presentation 不引入正文外结论，人物图片 alt 映射完整；
- 源 MDX、导入结果、门户资产与清单一致；
- 全文优化完成后才正式发布；发布器不得补写或改写业务内容。
