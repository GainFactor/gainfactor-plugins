# 增量工作流与阶段门禁

本流程用于避免“推进很多步后统一写报告”。每阶段按 `完成 → 检查 → 写入 → 进入下一阶段` 执行；失败时只返工受影响部分。

## 产物分层

- 正式报告：`docs/gainfactor/{product-slug}/user-persona.mdx`，只写已经通过门禁的读者内容。
- 首屏清单：`docs/gainfactor/{product-slug}/user-persona.portal.json`，随模块一和画像完成情况更新草稿，全文完成后统一校验。
- 人物图片：`docs/gainfactor/{product-slug}/assets/user-persona/`，单个画像稳定后生成。
- research sidecar：`docs/gainfactor/{product-slug}/.work/user-persona.research.json`，保存人物设定、原始反馈、归纳来源和门禁状态，不导入门户。

research sidecar 至少保持以下稳定结构，允许增加领域字段但不改写这些键的含义：

```json
{
  "schemaVersion": 1,
  "product": {},
  "researchMode": "agent-simulation | material-synthesis | mixed",
  "gates": [{"id": "G1", "status": "pending | passed | failed", "issues": []}],
  "agents": [],
  "feedback": [],
  "personas": [{"persona_id": "persona-*", "source_refs": [], "status": "draft | validated"}],
  "featureCandidates": [{"candidate_id": "candidate-*", "persona_id": "persona-*", "source_refs": []}],
  "normalizedFeatures": [{"feature_id": "feature-*", "merged_from": [], "persona_ids": []}]
}
```

`source_refs` 指向 Agent 回答、材料 `feedback_id` 或行为 Step；门禁每次失败和重新通过都更新对应状态与问题，不只记录最终结果。

## 阶段表

| 阶段 | 完成产物 | 通过门禁后立即写入 | 未通过时 |
|-|-|-|-|
| 产品上下文 | 产品定义、研究范围、读者任务 | 创建 MDX，写模块一已确定内容 | 补产品信息，不建 Agent |
| 人物设定 | 每个 Agent 的现实设定 | research sidecar | 修正失败人物，不运行其盲测 |
| 无产品盲测 | 逐步行为与原始反馈 | research sidecar | 针对缺失 Step 追问 |
| 产品命题测试 | 产品前后变化与顾虑 | research sidecar | 补测试，不命名画像 |
| 目标用户选择 | 画像选择、优先级、依据和唯一人物顺序清单 | 模块一目标用户与概览草稿 | 合并、减少或重做分类 |
| 画像内容 | 背景、情境、目标、路径、痛点、决策、功能期待 | research sidecar | 只补当前人物内容，不生成图片 |
| 人物导读 | 图片、PersonaBrief、Steps/Step、Panel 和板块蓝图 | 写入模块二对应人物 | 只返工当前人物的图片或表达 |
| 综合需求 | 共性与特殊问题 | 模块三需求综合分析 | 回查人物，不新造需求 |
| 功能归一化与优先级 | 稳定 feature_id、合并记录、P0/P1/P2/暂不纳入与风险 | 使用 Board 写入模块三路线图，必要时补人物 × 功能矩阵 | 修正来源、合并、优先级或重复项 |
| 整体优化 | 完整 MDX 与 Presentation | 更新最终源文件 | 不改变已验证业务结论 |
| 发布 | 门户路由、资产和清单 | 公共门户 | 保留源产物，说明阻塞 |

## 阶段门禁

### G1 产品上下文

能清楚说明产品、使用背景、当前解决方式、产品帮助、能力边界和本次画像要支持的决策。

### G2 人物真实性

逐人满足完整、现实一致、具体、可解释、有代表性、不刻板和彼此有实质差异。MBTI 只能辅助一致性。

### G3 当前行为路径

每个 Step 按情境适用地包含目标、工具或方法、使用方式、对象、反馈、判断、顾虑、决定和下一步；完整路径包含失败、替代或放弃结果。

### G4 产品反馈

每项反馈建立在当前路径上，明确介入步骤、行为变化、价值、顾虑和退出条件，不用功能反向制造需求。

### G5 目标用户选择

画像去掉产品仍成立，差异具有产品意义，不依赖人口属性、MBTI、阶段或接受程度；证据不足时减少画像。通过时冻结一份按用户优先级和阅读逻辑排列的人物顺序清单，后续模块一概览、模块二人物块、模块三人物引用和 Presentation cards 均从该清单生成，不得各自重新排序。

### G6A 画像内容

按 `persona-schema.md` 逐人检查背景、情境、目标、路径、痛点、决策与信任及期望功能。所有功能能沿人物路径推导。通过后才能生成当前人物图片。

### G6B 人物导读与表达

检查图片一致性、PersonaBrief 短事实去重、唯一图片 alt、人物章节标题、唯一人物内部标题、Steps/Step 连续性和 Panel 来源完整性。当前人物必须按 `人物三级标题 → PersonaBrief → 人物背景 → 典型情境 → 核心目标 → 关键行为与核心痛点 → 决策与信任关键 → 期望产品功能` 连续闭合；PersonaBrief 不重复章节编号，不得复制后文整段。当前人物的全部功能写完后才能出现下一个人物标题。

### G7 综合分析

共性问题至少由两个画像支持；特殊问题写明人物和条件；不得重新生成前文没有的需求，也不得用多数覆盖高风险特殊需求。

### G8 功能优先级

先按解决的问题和服务能力归一化跨人物功能；每项功能具有稳定 feature_id、明确人物来源、保留的差异顾虑、普通人可理解的描述、成立的优先级理由和真实风险。P0 构成核心价值闭环但不包揽全部需求。Board 只表达用户价值分组，不暗示研发排期或承诺日期；需要逐格核对时必须保留矩阵。

### G9 整体优化

检查三模块阅读路径、重复、推导断层、专业语言、案例泛化、组件必要性、桌面空间利用、移动端与打印可读性和 Presentation 一致性。逐板块确认阅读价值、信息关系、组件、选择理由和降级方案；核对人物顺序、人物块归属、章节编号连续性、目录与正文标题一致性、章节图标覆盖和标签语义；只优化表达与布局，不制造新事实。

### G10 发布

验证 MDX、图片、Presentation、组件语法、导入资产、门户清单和目标路由。正式发布前不得让发布器二次推导或美化普通 Markdown。

## 写入纪律

- 正式报告只写已通过门禁的内容；未确定区域不写占位结论。
- 后续证据推翻已写判断时，显式更新受影响章节和门禁状态，不静默保留冲突版本。
- 单个画像写入后允许局部优化，但跨画像综合只能在所有画像完成后进行。
- 人物顺序只有在用户优先级或阅读逻辑发生实质变化时才能调整；调整时一次同步正文概览、全部人物块、模块三引用和 Presentation cards，不允许只移动其中一处。
- Portal Presentation 可在写作中保存草稿，但只有全文完成、正文结论稳定后才作为最终清单发布。
