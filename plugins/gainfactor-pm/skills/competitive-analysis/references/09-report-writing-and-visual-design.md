# 正式报告写入与视觉表达蓝图

本参考定义 `COMPETITIVE_ANALYSIS` 各节点如何通过 `document-publisher` 直接写成可阅读、可核验、可决策的门户 MDX 报告。节点研究方法仍以 `SKILL.md` 与对应节点参考为准；本文件不新增流程，只约束最终 `.mdx` 的信息层级、组件选择和图文关系。

## 1. 报告与底稿的分界

正式报告回答四类问题：**结论是什么、为什么成立、证据在哪里、对产品决策意味着什么**。研究底稿保存检索词、候选来源、采集轮次、覆盖台账、完整测试协议、冲突处理、门禁记录和恢复点。

不得把以下内容写进正式报告：执行步骤、向用户索取材料的过程、完整网页摘要、全量截图、未采用证据、状态板、检查清单和修订流水。门禁未通过时保留真实状态，不用占位段落假装报告完整。

## 2. 每次写入前必须生成页面蓝图

每个正式写入节点先在底稿中填写并检查：

`读者任务 | 本节核心判断 | 信息关系 | MDX 组件或图形 | 选择理由 | 证据落点`

表达必须服务信息关系：

- 精确逐项核验或横向对照：最终 MDX 中的表格；
- 数量、趋势、结构、分布或层级：AntV Infographic；
- 连续主路径：`StructuredSteps`；存在分支、回路或跨主体交互时补 Mermaid；
- 多个同构分析单元：`ContentPanel`；多个并列类别：`GroupedBoard`；
- 产品身份与基础档案：`Profile`；紧凑范围、环境或元数据：`InfoGrid`；
- 截图证据：`ImageZoom`，必须紧邻它所证明的结论；
- 单个关键判断、限制或风险：`Callout`，普通正文不得全部包进 Callout；
- 互斥视角或模式：`Tabs`，不得用 Tabs 隐藏需要同时比较的信息。

组件只使用 `document-publisher` 已注册能力。页面蓝图完成后立即由 `document-publisher` 创建或更新最终 MDX 与门户条目，不创建普通 Markdown 中间稿，不等待全文完成后再转换。

## 3. 全篇统一阅读层级

每个正式章节按需要从以下四层取用，不机械凑齐：

1. **定位层**：标题、研究对象、范围、版本和证据窗口；使用短正文、`Profile` 或 `InfoGrid`。
2. **判断层**：本节最重要的判断及其产品含义；使用 1 个短结论段或 `Callout`。
3. **解释层**：数据关系、结构、流程、能力或比较；使用与关系匹配的图形和必要正文。
4. **核验层**：代表证据、截图、精确表格、引用和限制；证据就近放置，不在章节末堆成附件墙。

视觉规则：一张图只回答一个读者问题；图形负责关系，正文负责判断，截图负责证明，三者不重复复述。组件之间保留正常正文节奏，禁止把每段话卡片化。颜色只辅助层级，状态、分数和结论必须有文字标签。

## 4. A1 市场分析

### 固定阅读顺序

1. **市场口径**：用 1–2 段说明对象、地域、时间、统计口径和不可比限制；元信息可用 `InfoGrid`。
2. **市场规模**：先写一句规模判断，再用 AntV 的指标、趋势或分布图表达核心数字；图下注明口径和稳定引用。不得用宽表堆年度数字。
3. **市场机会**：将真正会改变产品判断的机会按主题组织为 `ContentPanel`；数量由证据与决策价值决定，不设固定上下限。每项按需要呈现 `机会信号 / 目标用户或场景 / 未满足任务 / 价值链位置 / 产品含义 / 证据强度`，弱相关信息不进入正文。
4. **上下游产业分布**：使用 AntV 关系图或层级图表达供给、能力、渠道、服务与用户的关系；突出主产品位置、关键控制点和依赖。
5. **市场判断**：使用一个 `Callout` 收束“优先机会、应控制或合作的环节、后续竞品检索方向、最重要限制”。

## 5. A2 竞品范围

本节的语义内容只保留用户已确认的精确表格；章节标题下允许一句不承载新结论的范围说明，但不增加候选分析、范围 Callout 或第二种视图：

`图标 | 产品名称 | 官网链接 | 产品定位 | 重合点 | 差异点 | 发展阶段`

表格承担范围确认，不改成卡片墙；图标使用已落地的本地资源，官网名称本身作为可点击链接。候选池、淘汰理由、融资和团队资料仍留在底稿。范围限制记录在底稿或后续实际比较处，不在本节追加分析型内容。

## 6. B1 单品基础分析

1. 用 `Profile` 建立当前产品身份：名称、图标、定位摘要、对象形态与官方入口；不得重复 A2 的整行信息。
2. 用 `InfoGrid` 呈现发展阶段、关键里程碑、证据窗口和研究边界。
3. **产品定位**：短结论回答“给谁用、解决什么、凭什么选择”，代表证据紧随其后。
4. **商业模式**：使用 `GroupedBoard` 分为主要、次要、探索中；每项写价值交换、付费方和可见证据。价格套餐细节留给 B5。
5. **竞争壁垒**：先用 AntV 条形或等级图表现六项 0–5 分，再用紧凑表格给出 `维度 / 分数或待验证 / 证据 / 理由 / 限制`。图用于扫读，表用于核验，两者不得重复长文。
6. 用一个结论段或 `Callout` 说明该产品当前依靠什么竞争、最脆弱的环节及对主产品的意义。

## 7. B2 功能分析

1. 用 `InfoGrid` 固定平台、版本、系统、账号、地区、采集日期和不可访问范围。
2. **功能结构总览**：使用 AntV mindmap 或层级图表达能力域与重点功能；正文只解释价值交付主线和最重要的结构判断。
3. **重点与差异功能**：按能力域使用 `GroupedBoard`；需要深入说明的功能改用 `ContentPanel`，字段固定为 `用户任务 / 入口与触发 / 输入 / 关键处理 / 输出与完成标准 / 边界 / 产品影响 / 证据`。
4. **关键用户旅程**：`StructuredSteps` 表达顺序、每步目标与反馈；只有存在关键分支、失败恢复、跨主体或交易状态时补 Mermaid。代表截图通过 `ImageZoom` 插在对应步骤或判断之后。
5. **技术实现判断**：使用普通正文或 `ContentPanel`，按 `用户可见能力 → 可观察机制 → 合理推测 → 证据等级 → 产品影响` 表达；推测不得画成确定架构图。
6. **覆盖与 AI 判定**：用短 `Callout` 写剩余限制及是否进入 B3，不展示采集轮次和覆盖台账。

每张截图必须有稳定证据 ID、产品/版本/系统/日期、画面说明和“它证明什么”；重复截图不进入正文。

## 8. B3 AI 探针

本节既要支持用户执行，也要在完成后成为领导可读的结果报告，因此分为两个状态。

### 计划状态

- 顶部用 `InfoGrid` 写产品模式、版本、账号、会话重置、测试日期与核验方法；
- 用 `GroupedBoard` 按定性能力、概率能力和产品闭环能力组织 11 个方向，只显示状态与样本要求；
- 每个 Case 用稳定 `ContentPanel`，首次仅填 `测试方向 / 指令原文与设计意图 / 预期表现 / 判定标准 / 状态`；多轮对话放在面板正文中按轮次列出；
- 不预建空白的实际表现、分数和截图区域，不显示一大片空表。状态为待执行即可说明尚无结果。

### 结果状态

- Case 完成后在原 `ContentPanel` 增加 `实际表现 / 判定 / 分数 / 产品影响 / 证据`，并就近插入 `ImageZoom`；
- 概率类能力达到有效样本门槛后，才用 AntV 比例或条形图呈现本轮小样本的首次可用率、核验通过率、幻觉率和任务完成率；不足门槛时只写逐例观察，任何情况下都不得外推为产品总体性能；
- 章节结尾使用 `Callout` 写 AI 能力边界、主要优势、主要风险和对 B2 的修订，不展示完整聊天实录。
- B6 收口时，将执行期的完整 Case 集合压缩为能力结论、小样本指标、代表性成功/失败案例和关键截图；其余指令、逐条记录和失败明细移入研究底稿，必要时仅在附录保留，不让最终领导版报告呈现测试过程。

精确样本明细可以在最终 MDX 中使用窄表，但不得做横向超宽表。

## 9. B4 体验分析

1. 用一个短结论段或 `Callout` 给出总体体验判断、关键亮点、最大摩擦和产品启示。
2. 核心体验链路用 `StructuredSteps` 表达；确有分支或恢复路径时补 Mermaid。
3. 第一印象、Onboarding、核心路径、信息架构、视觉设计、错误处理六项是分析检查框架，不要求形成六个等长章节。只有会改变体验判断的模块才展开为 `ContentPanel`，相关模块可按主题聚合为 `GroupedBoard`；字段按需要取用 `体验目标 / 实际表现 / 亮点或缺点 / 用户影响 / 产品启示 / 证据与限制`，不为对称而虚构或补齐。
4. `ImageZoom` 紧邻具体判断；同一截图只展示一次，其他位置用证据 ID 引用。

不要使用总分、截图墙或六行同质表格代替体验分析。

## 10. B5 增长分析

1. 用一个短结论段或 `Callout` 说明总体增长逻辑、核心回路、主要断点和证据强度。
2. 只有机制之间形成真实连接时，才用 AntV 或 Mermaid 表达 `获客 → 激活 → 留存 → 传播 → 付费`；不存在闭环时应画断点，不补全想象路径。
3. 获客、转化、留存、传播、定价是分析检查框架，不要求五项等长输出。只有会改变增长判断的模块才使用 `ContentPanel` 展开，相关模块可用 `GroupedBoard` 聚合；字段按需要取用 `目标行为 / 触发点 / 机制与路径 / 亮点 / 缺点 / 效果证据 / 产品启示 / 限制`。
4. 套餐、地区、计费周期和精确价格需要核验时使用紧凑表格；价格页截图用 `ImageZoom`。
5. 只有可靠结果数据存在时才用数据图；机制存在但效果未知时明确写 `【待验证】`，不制作伪指标。

## 11. B6 单品收口

B6 的检查清单、冲突修订记录和门禁结果只进入底稿。正式报告只新增当前产品的“四维总结”：

- 用 `InfoGrid` 呈现真实闭环等级、证据窗口、覆盖平台和主要限制；
- 用 `GroupedBoard` 按基础、功能、体验、增长四组表达 `一句话定义 / 关键优势 / 关键短板或边界 / 对主产品的意义 / 置信度`；
- 只有尚未解决且会改变判断的冲突，才用 `Callout` 就近提醒。

发现原章节有错误时直接修订 B1–B5，不在四维总结里追加“纠错说明”。

## 12. A4 阶段收口与横向比较

阶段性收口先用 `InfoGrid` 或简洁 `GroupedBoard` 呈现对象状态；未分析对象只显示名称、对象类型和真实状态，不创建空分析章节。

达到比较门禁后，基础、功能、体验、增长分别使用最终 MDX 中同一口径的精确矩阵；每个矩阵后写一段维度结论。若关系明显且数据充足，可增加一张 AntV 对比图帮助扫读，但图不能替代精确矩阵。未知、未测、不可比必须文字标记，不得填 0。

建议区不再用大表堆满页面：

- 可借鉴、不可照抄、差异化方向使用 `GroupedBoard`；
- 每条关键建议使用 `ContentPanel`，写 `优先级 / 机会来源 / 具体建议 / 预期用户价值 / 依赖或风险 / 验证信号 / 关联证据`；
- 行动项数量多且需要进入路线图时，再使用精确表格。

## 13. C1 最终成稿

最终报告建议顺序：

1. **竞品分析结论**：最后生成、放在最前；一个 `Callout` 给出总判断，随后按决策主题使用必要数量的 `ContentPanel` 呈现关键取舍与优先行动，不设固定数量。
2. **市场分析**：A1 成稿。
3. **竞品范围**：A2 成稿。
4. **单品分析**：每个已完成对象依次呈现 B1–B6；未完成对象按真实范围显示，不伪造结论。
5. **横向比较与建议**：仅在 A4 门禁满足时出现。
6. **关键限制**：只收录会改变决策的限制，并放在相关结论附近；无需再集中复述一遍。
7. **外部来源索引**：文档最底部的精确表格或定义列表，正文用稳定引用标记定位。

`.portal.json` 仅作为目录卡片和报告入口的补充，不承载正文。只有已有真实、稳定且对扫读有价值的信息时，才配置 `callout`、`cards`、`steps` 或 `metrics`；不得把章节数量、截图数量或研究时长包装成业务指标。

## 14. 发布前视觉门禁

- 每节的首个视觉元素能回答明确的读者问题；
- 同质内容已合理分组或转换表达方式，没有因机械卡片化造成阅读疲劳；
- 图、正文、表格和截图各自承担不同职责；
- 所有 MDX 组件属性符合注册契约，空值不渲染为占位内容；
- AntV 数据与正文一致，Mermaid 无语法错误，图片路径和 alt 有效；
- 桌面、移动端、明暗主题和打印/PDF 均可阅读；
- 最终 MDX 本身包含完整事实、结论、证据和限制，不依赖另一个 Markdown 版本；
- 页面没有研究过程、mock 信息、空章节、截图墙和超宽表格。
