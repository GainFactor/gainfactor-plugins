# Define Product

> **语言规则**：默认跟随用户输入语言；用户显式指定时以用户指定为准。稳定 artifact type 使用 `PRODUCT_DEFINITION`。详见 `../../references/language-policy.md`。

形成一份可被用户画像、竞品分析、市场研究和需求工作复用的产品定义。产品定义回答三个问题：**给谁用、解决什么问题、为什么是这个产品**。

本 Skill 定义产品，不展开详细功能、交互、技术方案、完整指标体系或项目排期。不要替用户决定新产品方向，也不要把公开营销表述当作已证实效果。

## 第一步：选择路径

完整读取 `references/interview-flow.md`，先判断产品状态：

- **新产品**：尚未发布，或只是准备加入已发布母产品的新能力。按访谈流程逐步定义。
- **已发布产品**：已经投入使用，可能是用户自己的产品，也可能是待分析产品。用户只需提供名称；完整读取 `references/released-product-research.md`，检索确认对象后自动补全。

若状态不明确，只问一次：“这是尚未发布的新产品，还是已经投入使用的产品？”不要同时抛出两条路径的问题。

## 新产品路径

先确认三项 Intake：主要产品形态、是否存在已发布母产品、主要服务对象。

存在母产品时，先按 `references/released-product-research.md` 的母产品流程自动补充公开背景，再只向用户确认无法从公开信息得知的内部依赖。随后按 `references/interview-flow.md` 完成六阶段访谈。

每轮最多询问 2 个相互关联的问题。只有答案会改变产品定义时才追问；未知内容可以保留，不能为了填满模板强迫用户选择。

## 已发布产品路径

收到名称后直接检索，不要求用户先介绍产品。先消歧产品、版本和地区，再自动补充定位、用户、问题、机制、场景、边界、采用循环和商业模式。

能继续检索解决的问题不询问用户。自动补全后，最多集中确认 3 个会改变核心定义的存疑项。外部产品的未公开信息不得要求用户猜测。

## 条件规则

- **内部效率产品**：正常完成产品定义；用内部触达、采用、持续使用和效率回流替代外部获客与增长，并跳过商业模式。
- **AI 能力**：只要产品提到 AI、Agent、模型生成、推荐或自动决策，读取 `references/product-patterns.md` 并执行 AI 价值判断。
- **产品类型**：按主要价值机制判断，允许跨类型，但必须区分首要类型和辅助类型。产品形态、服务对象、产品类型和母产品关系是四个独立维度。
- **商业模式**：只展开产品实际采用的盈利方式。SaaS 订阅与增值服务可以并存，但必须分别说明付费价值、计费单位和收费时点。
- **已有 PRODUCT_DEFINITION**：先读取现有状态。更新时展示变化及下游影响，只处理受影响部分；校验时只检查证据时效、一致性和准出项。未经用户要求不覆盖文件。

## 信息纪律

始终区分：

- `已确认`：用户明确确认，或可靠且无冲突的材料／公开证据；
- `明确排除`：用户明确不做的范围；
- `当前理解`：基于已有信息形成、等待确认的解释；
- `待定义`：尚无足够信息，或只有工作假设；
- `待确认冲突`：两个不能同时成立的定义或证据。

不得把推断写成事实，不得重新引入已排除范围。发现冲突时展示双方和影响，让用户决定；分析外部已发布产品时，无法解决的冲突保留在文档中。

## 输出

输出前完整读取 `references/artifact-schema-and-quality.md`，按其中结构生成 `PRODUCT_DEFINITION`。

- 新产品只有通过准出检查并由用户确认后，状态才为 `confirmed`。
- 已发布产品只有对象明确、核心字段有可靠证据且关键冲突已解决时，状态才为 `confirmed`。
- 其他情况交付 `draft`，明确缺口及其影响。

业务定义通过质量门禁后，进入门户正文成稿阶段。完整读取 `$document-publisher` 的表达设计、能力目录、工具目录、正文契约和发布流程，先形成页面蓝图，再直接写出最终门户正文；不得先生成朴素 Markdown，再把语义组织或表达设计交给发布 Skill 二次转换。

- 只使用标准 Markdown 与 Mermaid 时输出 `.md`；使用 Callout、Cards、Steps、Tabs、AntV Infographic、NodeGraph 等已注册组件时输出 `.mdx`。
- 只有首屏摘要能明显改善扫读时，才生成同名 `.portal.json`；其中不得出现正文没有的新事实。
- 每一种增强表达都必须服务于明确的阅读任务。正文必须可独立阅读，关键结论不能只存在于图表、组件或门户清单中。
- 不追求组件数量。短段落或普通表格已经足够清晰时，保持简单表达。
- 选择 AntV Infographic 时，必须先读取 `$document-publisher` 对应的语法参考；不确定语法或渲染能力时使用稳定回退表达。

### 自动交付（默认执行）

产品定义通过质量门禁后，默认连续完成以下动作，不询问用户是否生成文档：

1. 按页面蓝图直接形成完整的最终门户正文；根据实际表达使用 Markdown 或 MDX，不生成等待后续转换的中间版本。
2. 调用 `$document-publisher` 将这份最终正文直接写入公共文档门户；文档类型使用 `Product-Definition`，集合使用“产品文档”，布局使用 `report`，稳定 slug 使用小写字母、数字和连字符。
3. 已知当前任务正在使用某个 GainFactor 文档门户时，直接写入该门户；否则创建独立临时门户并写入。不得为了选择门户再向用户提问。
4. 从实际门户路由读回正文，校验标题、章节、元信息、关键结论和可选首屏呈现均已正确写入；再返回核心结论和门户路由。若发布实现同时保存了正文源文件，可一并返回其位置，但不得把它描述为导入源或转换中间稿。

自动写入门户不等于自动启动服务。只有用户要求预览、打开或启动时才安装门户依赖并启动本地服务。

只有用户明确要求“仅在对话中输出”“不要写入门户”或给出其他交付方式时，才按其要求缩减自动交付。写入前确保目标门户和发布实现使用的目录处于当前任务允许的范围内；写入失败时说明具体阻塞并保留已经成功形成的最终正文，不回退为人工确认流程。

### 可选下一步：产品指标

产品定义完成并写入门户后，若 `Subject Relationship: own` 且核心用户、问题和价值机制足以支撑衡量，只询问一次：“产品定义已经完成，是否继续基于这份定义建立产品指标体系？”提供“继续定义产品指标”和“暂不继续”两个选择。

- 用户选择继续时调用 `$product-metrics`，传入当前 `PRODUCT_DEFINITION` 和门户路由；不得重复询问其中已经确认的定位、角色、场景、价值结果、商业模式或失败边界。
- 用户暂不继续时结束当前流程，不影响已完成的产品定义。
- `analysis-target`、存在高影响核心冲突，或用户已明确只需要产品定义时，不主动提供该选项；用户仍可显式调用 `$product-metrics`。
- 这是新的下游任务选择，不是文档生成或发布确认；产品定义仍按前述规则自动写入门户。

## 下游复用契约

下游任务把 `已确认` 的定位、用户、问题、机制和边界作为事实基线，不重复询问、不静默改写。`$product-metrics` 还应复用可观察结果、角色关系、生命周期、商业模式与失败边界，只补充战略目标、候选指标、数据能力、基线和阈值依据等指标专属信息。新证据与定义冲突时，列出冲突并请求确认。除明确要求它作为门禁的下游 Skill 外，`PRODUCT_DEFINITION` 是可选上下文。
